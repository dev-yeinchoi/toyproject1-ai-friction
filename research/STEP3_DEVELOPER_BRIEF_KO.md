# Step 3. 개발 명세 및 검증 프로토콜

## 연구 목표
AI 권고 **수용**과 **사유 제출형 이의제기**의 구조적 마찰이 UI 설계 요인에 따라 어떻게 배분되는지, 실제 브라우저 조작과 상태 전이 모델을 사용해 재현 가능하게 분석한다. 참여자 모집 없이 수행한다.

## 독립적인 설계 요인
1. **이의제기 진입 접근성:** 간접(U1/U3) vs 직접(U2/U4)
2. **수용 전 근거 검토:** 선택(U1/U2) vs 필수(U3/U4)

고정 조건: 프로젝트 안내문 외부 공유 승인 권고. 테스트용 근거 상태 3종: E1(허용/완료), E2(제한/완료), E3(미확인/완료). AI 권고는 모든 상태에서 승인으로 고정한다. 이들 데이터는 독립변수 효과의 통계적 추정을 위한 조건이 아니라 UI 정보 표시·경로 동작의 기능 테스트 입력이다.

## 4개 UI 및 고정 기대 경로
| UI | 이의제기 진입 | 수용 전 검토 | 수용 최단 클릭 | 이의제기 최단 클릭 |
|---|---|---|---:|---:|
| U1 | 간접 | 선택 | 1 | 4 |
| U2 | 직접 | 선택 | 1 | 3 |
| U3 | 간접 | 필수 | 3 | 4 |
| U4 | 직접 | 필수 | 3 | 3 |

이의제기는 (진입)→(사유 라디오 선택)→(제출) 동작. 간접 진입 시 기타 메뉴를 열고 메뉴 안의 이의제기를 눌러야 한다. 필수 검토는 (수용 시작)→(근거 화면)→(검토 완료)→(최종 수용)으로 구현한다. 이 단계가 내용을 이해했다는 증거는 아니다.

## 핵심 구현
- React + Vite + TypeScript, 상태는 인메모리로 관리. 실제 외부 문서 전송, LLM 호출, 외부 추적 없음
- S0 추천 / S1 근거 / S2 사유 선택 / S3 수용 완료 / S4 이의제기 완료
- M1 기타 메뉴 / R1 검토 완료 / S2R 사유 선택 완료 보조 상태
- UI 전체 디자인을 동일하게 유지하고 진입 접근성과 검토 단계만 다르게 조작
- URL `?ui=U1&evidence=E1` 등으로 조건 재현
- `window.__researchDebug.getEvents()`에 UI 조작 이벤트를 인메모리로 수집. 이는 Playwright의 합성 동작 로그이며 사람의 행동 자료가 아니다

## 재현 순서
1. `npm install`
2. `npx playwright install chromium`
3. `python3 scripts/graph_model.py` → 기대 경로 8개를 그래프 탐색으로 계산
4. `npm run test:paths` → 24개 브라우저 정상 경로 검증 및 개별 JSON 저장
5. `npm run test:guards` → 제출 차단/검토 단계 우회/근거 표시/직접주소 테스트
6. `npm run analyze` → **실제로 수집된 24개 PASS 기록이 모두 있어야만** CSV·Figure 생성

## 결과 해석
- `graph_expected.csv`는 **모형 기반 기대값**; 실험 결과 아님
- `cases.csv`는 **자동화 브라우저 조작의 실제 기록**; 사용자의 관찰 행동이 아님
- `comparison.csv`는 UI별 클릭 수/차이를 정리한 **기술적 비교표**
- 정규성 검정, t-test, ANOVA 등을 적용하지 않음. 24개는 독립적 참여자 자료가 아님
- 클릭 수 비대칭을 공정성 점수로 부르지 않음. 이의제기는 사유 선택·제출 자체로도 수용보다 2클릭 더 필요할 수 있음
- 필수 검토 우회 시험은 일반 UI·브라우저 조작 기준의 기능 검증이며 서버 보안을 입증하는 시험이 아님

## 결과 해석 시 주의
구현자가 설계한 클릭 비용을 브라우저로 재확인하는 연구이므로 발견의 새로움은 제한적이다. 본 연구의 기여는 사용자 행동 효과가 아닌 절차적 마찰의 **명시적인 모델링, 독립적인 브라우저 검증, 재현 가능한 결과 패키징**이다.
